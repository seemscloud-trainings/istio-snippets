# Istio Snippets

This repository contains small, independent Istio training examples. Follow the sibling istio-setup documentation style: README.md is a links-only index; topic pages start directly with short preparation/example headings. Use English for descriptions and diagrams. Sidecar examples live in sidecar/; PeerAuthentication plus AuthorizationPolicy in peer-authorization/; JWT plus AuthorizationPolicy in request-authorization/. Each has a root README topic page with three YAML examples and a diagram per example. These are alternative configurations, not cumulative installations. ServiceEntry variants are alternatives for the same host, not a combined installation. Preserve the current branch and unrelated changes; commit/push only when requested.

service-entry/*.yaml are the canonical copyable manifests. README.service-entry.md contains only example headings, YAML blocks and PNGs from images/service-entry/. scripts/render_service_entry.py renders the five diagrams and regenerates the topic page from these manifests. Each Pod shows a Container running plain curl http://wp.pl or curl https://wp.pl, its resolved IP, Envoy and the upstream socket. Above Envoy, a ServiceEntry block lists only relevant inputs (hosts, resolution, addresses/endpoints or port translation); Envoy shows the effective host-to-IP mapping instead of endpoints/configuration fields. ServiceEntry traffic arrows use HTTP/HTTPS, including HTTP-to-HTTPS origination; TLS remains only in actual configuration field names. Security and Sidecar diagrams explicitly distinguish HTTP from mTLS, and show where Envoy rejects a request before the API is reached. Resolver labels must be just DNS. Public examples must contain only short headings, comment-free YAML and diagrams. Explain behavior through diagram flows; never add explanatory YAML comments, prose, footers, callout cards or legends. Keep setup assumptions in this AGENTS.md. The offline Pillow/PyYAML renderer uses illustrative RFC 5737 DNS answers: wp.pl = 198.51.100.10 and backend.wp.pl = 198.51.100.20; these are not real DNS measurements. Assume sidecar mode with DNS capture disabled. For NONE, compare the curl DNS IP with the listed addresses and show that this ServiceEntry is not used when they differ. Draw separate outbound-policy outcomes: ALLOW_ANY keeps curl's original destination, REGISTRY_ONLY blocks the connection. Do not use unexplained no-IP-match shorthand, fabricate DNS rewriting or use --resolve. Name this example Original destination, not Service Translation. DNS endpoint overrides must explicitly show the different backend hostname's resolved IP beside that endpoint in the ServiceEntry block. STATIC selects the configured destination, and TLS origination uses targetPort to change ports.

Regenerate with python3 scripts/render_service_entry.py using an existing Python environment with Pillow and PyYAML; do not install dependencies without authorization. PNG output is reproducible with the same Pillow and fonts (Arial on macOS, DejaVu Sans fallback on Linux); --check compares generated Markdown and image pixels without writing files. Review every rendered image, parse the YAML, validate against locally available Istio schemas when possible, and review Git diff/status before committing. Do not apply manifests, start services, or contact example endpoints during verification. scripts/render_policy_examples.py generates the nine additional PNGs and three topic pages, with the same --check workflow and shared Canvas. Assume existing HTTP Services api.shop, api.payments and api.reporting, exported to shop, with Service port 80 mapping to Pod port 8080; APIs return 200 when reached on the illustrated routes. These fixture assumptions belong here, not in YAML comments. JWT placeholders VALID/ADMIN/USER are signed and unexpired with the configured issuer/audience; INVALID has a bad signature. ADMIN has role=admin and USER has role=user. Invalid JWT remains rejected on public /healthz. Use illustrative DNS Service IPs, trust domain cluster.local, automatic client mTLS and no additional matching policies. Sidecar is configuration scoping, not a security boundary; its ALLOW_ANY example explicitly assumes a plaintext-capable destination. Strict mTLS rejection is a transport failure, RBAC denial is HTTP 403, invalid JWT is HTTP 401, and missing JWT requires an AuthorizationPolicy to be rejected. JWT issuer/JWKS URLs and shell token variables are placeholders. The documentation describes intended routing, not a verified live environment.
